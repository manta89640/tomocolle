# Overlays 98 and 99 (the settings, the mansion information): working notes

## How the compiler orders a file's data (measured)

- A file's data objects are kept in a list in declaration order, the file statics first, then the anonymous and
  function-local ones as they are made, the class's virtual table last. The list is reversed (newest first) and
  sorted by size with a plain max-heap sort (build the heap by sifting down from n/2 - 1, then swap the root with
  the end and sift down), ascending. Simulated in Python, this reproduces our compiler's output for overlay 98's 30
  statics plus five anonymous local initialisers exactly, and overlay 99's.
- Because the permutation depends only on the sizes, any target order of same-sized objects can be had by solving
  for the declaration order: run the sort on indices with the intended key sequence, then put each target name at
  the input position that lands where the target wants it. Overlay 98's statics are declared in such a solved
  order (the order looks arbitrary in the source for that reason).
- Our compiler (2.0 SP2p2, "3.0 build 137") pools every four-byte-aligned object of `.rodata`; a 1-aligned
  `char` array gets a section of its own at its sorted place, after the pool. Build 138 (SP2p3) keeps objects of
  64 bytes and more out of the pool, each in a section of its own in sorted order; that is what overlay 98's ROM
  shows: the string "N83:/Window_down.nsc" (21 bytes) after the pool and before the six big tables.
- Function-local `const` scalars (`const int k = 2;`) are emitted as pool entries even when every use is folded;
  file statics read only through folded fields are also emitted. An unreferenced file static is dropped; `(void)x;`
  keeps it and makes no code.
- `extern const` and function-local `static const` objects are pooled like file statics.

## Overlay 98's pool

`0x0214C15C`: 36 bytes nothing refers to, as words 0, 2, 0, 0, 4, 2, 2, 2, 2. Then the 8-byte objects, read off the
pool's start by OpenWindow: the text position of the clock question (+0x24), of "set the time" (+0x2C), of the
other questions (+0x34), the OK button (+0x3C), the button size (+0x44, also copied whole), the text of the windows
without buttons (+0x4C), and the yes/no message numbers {2, 3} (+0x54). The 36 bytes fit nine 4-byte objects
(they sort first): three zeros, one 4 and five 2s. The 4 and four of the 2s could be the digit counts of the five
digit displays (ShowYear has four digits, the others two) as function-local `const int`s; that is a guess, and the
rest is not identified. With five such locals made in the order 4, 2, 2, 2, 2 and the zeros as statics, a random
search of 200,000 declaration orders found none that gives the ROM's words, so that guess is at least incomplete.
The source keeps the 36 bytes as five statics with the ROM's values instead.

## Matching notes

- Registers and stack slots follow declaration order: each loop with its own `for (int i ...)` gave the ROM's
  registers throughout Init, SetState (and HideAll) and Draw; overlay 99's counters had to be declared men before
  women, and its temporaries C-style at the top in the order troubles, residents, averageAge, year.
- An if/else that the ROM compiles as "then predicated, branch over else" comes from writing the branches the
  other way round (`if (year != 0) year--; else year = 99;`, `if (!female) men++; else women++` style).
- A copy passed by value to an inline is placed below the caller's own locals: OpenWindow's yes/no helper is an
  inline because of that (one of its two copies of the button size is lower than the other).
- `NNS_G2dStopAnimCtrl(NNS_G2dGetCellAnimationAnimCtrl(&sprite.mAnim))` gave the ROM's base register where
  writing the field did not.
