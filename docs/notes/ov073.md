- (b1) THE POOL AT THE START OF .rodata (data_ov073_02150ba4), for b0 and b2 (measured with the compiler): an initialiser of a small LOCAL structure (`FloorPos target = { 0, -0x4800 };`, also ScreenPoint/ScreenRect-sized ones) is an anonymous object `@N`; the compiler puts all of them of up to 8 (16?) bytes into one pool at the start of .rodata and the code reads them as `ldr rX, =pool; ldr [rX, #offset]`. That is why 0x0214a770 (b0), my 0x0214d6a4 and b2's 0x02150348 / 0x02150448 all hold 0x02150ba4 and use offsets from it: the whole overlay is ONE translation unit. The order of the pool's entries follows the compiler's numbering of every anonymous object in the file (it changes when an unrelated function is added before), so a part compiled alone gets other offsets. To match in a part, declare the pool as an extern structure at 0x02150ba4 and read the member (my `SmallConstants` in b1/RoomCharacter.h: +0 s16[2] {2,3}, +4 FloorPos, +0xC ScreenRect-like {0x26,0x21,0x5e,0x1e}, +0x1C {0x80,0xb1}, +0x24/+0x2C/+0x34 FloorPos, +0x3C {0x80,0x95}); a local copy of the member (`FloorPos target = pool.mX; Set(target);`) gives the same code as the local initialiser. 12-byte locals (`VecFx32 pos = { 0, 0, -0x9000 };`, copied with ldm/stm) are anonymous objects of their own (0x02150bf4, c00, c0c) and match as written.

## Joined into one file (the finishing pass)

- The three parts are one file, `src/overlays/ov073/TutorialRoomScene.cpp`, in address order, with every section of
  the overlay in `delinks.txt`, and one set of headers beside it. The classes are named in the source
  (`TutorialRoomCharacter`, `TutorialRoomCamera`, `TutorialApartmentRoom`, ...): the program is linked as one, so
  overlay 73's versions cannot share overlay 74's names. `TutorialNames.h` is gone.
- 131 of 133 match. Still differing: `TutorialApartmentFront::UpdateCursorTarget` and
  `TutorialClockDisplay::Refresh` (comments above them say how), both byte-identical to overlay 74's.
- The scene's destructor (D1 0x02150a1c, D0 0x02150adc): declared `virtual ~TutorialRoomScene()` and defined empty
  at the end of the file, with the door model a member of `RoomDoorModel`, not its base (overlay 74's finding):
  otherwise the inlined door destructor stores a virtual table of its own.
- `TutorialNamePanel::Init`: both character counts read the canvas through a pointer (`GetCharCount` in the file)
  and both positions are set with `SetPositionFromVec`.
- `HeadIcon::Load` and `TutorialRoomCharacter::LoadHeadIcon` take the `ParticleSystem *`: symbols renamed
  (`_ZN8HeadIcon4LoadEP14ParticleSystemi` in the main program).
- MEASURED, how this compiler lays out a file's data (2.0 SP1p2, SP2 and SP2p2 alike, with small test files): it
  keeps the file's data objects (`.rodata` and `.data`, virtual tables, VTTs and construction tables included) in a
  list, newest first, named objects at their declaration and the anonymous initialisers after all of them, and
  heap-sorts the list by size (a plain max-heap sort, ascending). Objects of four-byte alignment in `.rodata` are
  pooled into one object, in that order, at the place of the first of them; every other object gets a section of
  its own, in that order. An unreferenced `static` is dropped; an unreferenced external object gets a section of its
  own. Since the sort's permutation depends on the sizes only, swapping two objects of the same size in the
  declarations swaps their places: that is how the file's constants are ordered now (all declared together at the
  top), and it puts the pool's eight 8-byte points where the ROM has them, which made `Init` (six loads) and
  `UpdateStates0ATo0F` (two) match.
- MEASURED, the ROM's layout, which that does not give: `.rodata` is the pool (0x02150BA4 to 0x02150CE4: sizes 4,
  8 x 8, 10, 12 x 5, 16 x 4, 22, sorted), then `sButtonRectOther`, `sButtonRect0`, `sButtonRect1` (16 each),
  `sRoomCounts` (4), `"MLT:/Window_down2.nsc"` (22), `sSkyPictures` (32), `sClockPositions` (88), which are not in
  order of size; `.data` is the MessageText construction table (24), `gWalkArea` (16), TutorialTimedMessage's
  table (24) and VTT (24), the ObjTextCanvas and BgTextCanvas construction tables (12, 12), the room's table (36)
  and the scene's (36), not in order of size either. With our compiler every object comes out in one size order,
  so the data does not match and the unit is not `complete`. Overlay 74 shows the same kind of unsorted runs.
  The pool also holds two objects that nothing refers to, the camera's orbit limits {0x40000, 0x100000, 0} and
  {0x4000, 0x7000, 0} (kept here as file statics whose values `UpdateOrbit` folds), and the ROM keeps the
  unreferenced `sButtonTouchRect` (in the pool) and `sButtonRect1`, which a `static` cannot give.
- Data and the main program's symbols named: the statics as local symbols (`sButtonSequences` ... `gWalkArea`),
  the virtual tables and the VTT by their compiled names, with addends in `relocs.txt` for the references into
  them; the main program's `_ZN17TutorialRoomSceneC1Ev` (func_0203efc0), `_ZN21TutorialRoomCharacterD1Ev`
  (func_0203f1c0), `_ZN8RoomPartD1Ev` (func_0203ef80).
