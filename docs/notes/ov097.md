# Overlay 97 (the staff credits after a wedding): working notes

## What the scene is (from its code)

- Scenes 0xC0 and 0xC1, `Marriage2Scene`. The wedding (scene 0xAB, overlay 96) asks for 0xC0 after it hands over
  the album. The scene asks for 0xAB again when the music stream ends or the skip button has been pressed.
- The lower screen scrolls the credits: 13 sprite texts 16 pixels apart go round a 208-pixel loop. Each one takes the
  next message of "TBM:/tmd_staff_msg_JP.bmg" when it comes back to the bottom, and the credits end after message 172.
- The upper screen shows 21 pictures ("Scn/Mrg/mrg00_LZ.bin" to "mrg20", mounted as "3BG"). Each is a background,
  a body model drawn twice, and the couple's two faces from `FaceCast`, placed by `sFacePoses`. `sPictureTimes`
  says which picture comes next and the frame by which it must be up.
- The skip button is hidden the first time and shown after that (`gGameData.mUnknownB2[1]`, set by this scene).
- Scene 0xC1 starts in a state that does nothing (`STATE_NONE`).

## Data

- Measured: the .rodata pool also holds the 120 face arrays of overlay 71's right-job pictures (overlay 71 reads
  them through a 120-entry table at `0x0214BD78`), byte for byte. Overlay 97 has the arrays but not the table, and
  no code of overlay 97 reads either.
- Measured with the build's compiler: arrays that only an unreferenced static table refers to are dropped together
  with the table. They stay in the pool only when a function refers to the table. The link then strips that
  function and the table's own section (it is 64 bytes or more), and the arrays stay in the pool. So the file had
  such a function (`Marriage2Scene_UnusedGetJobFaces` stands in for it).
- Inferred: the file was made from overlay 71's source. The two scenes have the same layout, and both load
  "3BG:/bg.nsc" and "3BG:/body.imd".
- The u16 4 and int 16 at the pool's start are referred to by nothing. They are written as `sButtonKinds` (the
  button's kind is 4) and a local `const int lineHeight` of `ScrollCredits` (the lines are 16 pixels apart). Both
  are guesses from the values; no code shows them.
- All 127 pool objects went to the ROM's places in one pass: compile, read which declaration each slot of the
  compiled pool holds, find the declaration whose bytes the ROM has in that slot, and swap the declaration lines
  (the sort's permutation depends only on the sizes). A short script did it. It matched objects by their bytes and
  needed nothing else, since the order of each size class is free.
