# Overlay 72 (the island map): working notes

## How the compiler places a file's data (measured, with 2.0 SP2p2 and SP2p3)

This model reproduces the place of every data object of `MapScene.cpp`'s compiled object, with no exception:

1. The compiler keeps a list of data objects, newest first. Each `static` (or external) object goes on it when it
   is declared, and just before it go the anonymous strings of its initializer, in their order (so in the list,
   newest first, the object comes before its strings). A static that nothing refers to is not on the list.
2. After the file's statics: the virtual table of the class whose key function is defined, then the local `const`
   objects of the functions (`const int x = 1;` inside a function), in the order they appear. A local `const`
   scalar is emitted as an object (`x$13757`) even when every use of it is folded, and nothing refers to it.
3. The list is heap-sorted by size: a plain max-heap sort, ascending, with the strict comparisons of the textbook
   version. Among objects of one size the result is a fixed permutation of their places in the list, which is why
   swapping two declarations of the same size swaps their places, as long as no string goes with them.
4. The four-byte-aligned objects of `.rodata` are pooled into one section, in that order, at the place of the first
   of them; those of `.data` too (the pointer tables). Every other object gets a section of its own. With 2.0
   SP2p3 (and the DSi compilers) objects of 64 bytes and more are not pooled; with SP2p2 and before they are.

Code literals (strings in function bodies) are not on the list: they come after it in `.data`, in the order of the
functions.

Checked on a five-object test file (declarations A..E all of one size give D C B A E) and on the whole file.

## Solving the declaration order

With the model a declaration order can be searched for without compiling: simulated annealing over the order of the
file's static declarations (and of `Init`'s four local constants), scoring the `.rodata` pool's order, the `.data`
pool's order and the order of the sorted `.data` strings against the ROM. The pools come out right in seconds of
search; the strings are 47 of 112 so far (they only matter for marking the unit complete). The scripts were scratch
work, not kept in the repository; the model above is all they used.

## Idioms that made functions match

- A one-element static array read in a one-iteration loop is loaded, not folded: that is how the original reads
  `ldrh rX, [pool, #2]` for the back button's sequence and `[pool, #0x10]` for the title's font.
- `SpriteButton mBackButtons[1]` handled in a loop of one keeps the element's base in a register, as the original's
  Update does.
- `(x == 1 || x == 2)` on a `u8` gives `add r0, r0, #255; and; cmp #1; bhi`; `(u8)(x - 1) <= 1` gives `sub`.
- A switch whose `default` comes first in the source puts the default's code right after the compare chain
  (`EnterBuilding`); `case 7: case 10:` before `case 2:` likewise (`OpenWindow`).
- `MessageWindow_SetTextPosition` takes a text position as two ints: passing `position.x, position.y` of a by-value `WindowPoint`
  gives the original's dead stack copy (`OpenWindow`).
- `x * 5 * FX32_CONST(0.01)` keeps the original's `add x, x, x, lsl #2` and `mul #41`; `x * 5 * 41` is folded to
  one multiplication by 205 (`GetWindowPosition`).
- `hour * 3600 + minute * 60` computes the minutes first; `minute * 60 + hour * 3600` the hours first.
- A local that receives a struct's field before both stores (`int value = ...; mValue = value; mTarget = value;`)
  gave `MapSound::Init`'s order; chained assignment did not.

## Scene ids

0x5F to 0x61: the island. 0x62 to 0x66: the island at sizes 0 to 4 (no saved data is read). 0x6A: the title mode
first. 0x6D, 0x6E: the tutorial's visits. It asks for 0x11 (the apartment), 0x46 (the news, overlay 87), 0x69
(after the tutorial), 0xC2 (from the title, when func_0202cd54 says so), 0x2C (START), and each building's scene
(`EnterBuilding`).
